# Авточек — состояние ядра

Дата фиксации: 2026-08-19.

## Целевая цепочка

`источник автомобилей → импорт карточек и фото → каталог Авточек → карточка автомобиля → запрос отчёта → проверка доступности и цены → оплата клиента → создание оплаченного заказа → авторизованный запрос исходного отчёта → получение исходника → парсинг → перевод → нормализация → анализ → отчёт Авточек → выдача клиенту`

Публичный пользователь работает только с интерфейсом Авточек. Техническая связь с источниками хранится внутри backend.

## Резолюция

Сейчас хорошо собран frontend-каркас продукта: лендинг, VIN-сценарий, каталог, карусель, карточка автомобиля, CTA заказа отчёта, визуальная модель отчёта и правила скрытия технических источников.

Операционное backend-ядро пока находится на уровне архитектуры и интерфейсных заглушек. Реального импорта живых машин, базы автомобилей, заказа, платежа, авторизованного получения исходного отчёта и автоматического report pipeline в репозитории пока нет.

## Статусы

### 1. Лендинг и основной пользовательский вход — ВЫПОЛНЕНО

Есть главная страница Авточек, VIN-форма, валидация VIN, светлая/тёмная тема, информационные блоки и основной CTA.

Осталось: позднее провести финальный UX/темный проход и мобильную оптимизацию.

### 2. Вход по VIN — ЧАСТИЧНО

Выполнено:
- клиент может ввести VIN;
- frontend валидирует 17 символов и формат;
- существует состояние `VIN → Проверка → Отчёт`;
- VIN сохраняется как контекст будущего заказа.

Отсутствует:
- backend `Vehicle Resolver`;
- определение автомобиля по VIN;
- реальный запрос доступности данных;
- получение модели/комплектации/характеристик после VIN.

### 3. Исследование источников автомобилей — ЧАСТИЧНО

Выполнено:
- исследованы публичные карточки китайских площадок;
- выделены основные поля предложения;
- проверена возможность получать фото, характеристики, цену, город, данные состояния и inspection-поля;
- создана схема `vehicle_id → source_id → source_listing_id`;
- выбрана реальная карточка Audi A6L как референс структуры.

Отсутствует:
- подтверждённый production-канал доступа к inventory;
- договорённость/API/разрешённый способ массового получения данных;
- стабильный способ обновления наличия и цен;
- подтверждённый доступ к VIN конкретной машины;
- подтверждённая связь карточки продажи с покупаемым историческим отчётом.

### 4. Catalog Collector — НЕ ВЫПОЛНЕНО

Нужен отдельный backend-сервис, который:
- получает новые объявления;
- обновляет существующие;
- забирает доступные фото и характеристики;
- фиксирует источник и `source_listing_id`;
- отслеживает изменение цены;
- отмечает снятые с продажи автомобили;
- пишет `last_seen_at` и `updated_at`;
- передаёт наружу только нормализованный объект Авточек.

Сейчас каталог использует демонстрационный массив JavaScript.

### 5. База автомобилей — НЕ ВЫПОЛНЕНО

Нужны постоянные сущности минимум:
- `vehicles`;
- `vehicle_listings`;
- `vehicle_photos`;
- `vehicle_specs`;
- `listing_snapshots`;
- `source_connections`;
- `report_linkages`.

Сейчас `vehicle_id` существует только как frontend-концепция/демо-ID.

### 6. Каталог Авточек — ЧАСТИЧНО, FRONTEND ГОТОВ

Выполнено:
- отдельная страница `cars.html`;
- пункт «Автомобили» в навигации;
- карусель автомобилей на главной;
- поиск;
- фильтр по городу;
- сортировка;
- карточки автомобиля;
- кнопка `Запросить отчёт`;
- отсутствие публичных ссылок на внешний источник.

Отсутствует:
- загрузка из backend API;
- реальные фото;
- реальные актуальные статусы наличия;
- серверная пагинация;
- полноценные фильтры по марке, году, цене, пробегу, типу кузова и т.д.;
- дедупликация предложений.

### 7. Страница автомобиля — ЧАСТИЧНО, ЭТАЛОННЫЙ FRONTEND СОБРАН

Выполнено:
- отдельная `vehicle.html`;
- desktop-галерея с крупным фото, миниатюрами, переключением ракурсов и счётчиком;
- цена вынесена в основной purchase-блок;
- главный CTA расположен непосредственно рядом с ценой;
- ключевые характеристики;
- предварительные сведения о состоянии;
- оснащение;
- вторичный блок сценария отчёта;
- сохранение выбранного `vehicle_id` в sessionStorage.

Критический текущий предел:
- страница пока статична и построена на одной Audi A6L;
- разные карточки каталога ещё не подставляют собственные данные в `vehicle.html`;
- реальные фотографии через API пока отсутствуют;
- VIN может отсутствовать и пока не разрешается системой.

Следующая задача этого блока: `GET /vehicles/:id → VehiclePublicDTO → render vehicle.html`.

### 8. Публичное скрытие партнёрской инфраструктуры — ВЫПОЛНЕНО КАК ПРАВИЛО

Зафиксировано:
- в каталоге не показывается название внешней площадки;
- нет её логотипа;
- нет внешней ссылки;
- пользователь выполняет все действия через Авточек;
- технический источник хранится только в backend;
- место продажи может быть раскрыто внутри готового отчёта как происхождение записи, если это потребуется продукту.

### 9. Report Availability — ЗАГЛУШКА

Frontend уже содержит шаг проверки доступности отчёта.

Нужен backend endpoint примерно:

`POST /report-quotes`

Вход:
- `vehicle_id` или VIN.

Выход:
- `available`;
- `quote_id`;
- `price`;
- `currency`;
- `expires_at`;
- `expected_delivery`;
- причина невозможности получить отчёт.

Публичный ответ не содержит название внутреннего поставщика.

### 10. Order Service — НЕ ВЫПОЛНЕНО

Нужны постоянные заказы:

`customer + vehicle_id + quote_id + price → report_order`

Статусы:
- `awaiting_payment`;
- `paid`;
- `queued`;
- `purchasing_source_report`;
- `source_report_received`;
- `processing`;
- `ready`;
- `failed`;
- `refund_required`.

Нужна защита от двойного создания и двойной покупки одного отчёта.

### 11. Оплата клиента — НЕ ВЫПОЛНЕНО

Нужно:
- платёжный провайдер;
- создание платежа;
- подтверждение платежа по webhook/API;
- фиксация суммы;
- идемпотентность;
- возврат средств;
- переход заказа в `paid` только после подтверждения провайдера.

Ключевое бизнес-правило уже зафиксировано: внутренний платный запрос исходного отчёта разрешён только для `paid`-заказа.

### 12. China Source Worker / авторизованный аккаунт — НЕ ВЫПОЛНЕНО

Это центральный технический блок будущего ядра.

Нужно:
- безопасное хранение авторизованной сессии;
- открытие нужной исходной карточки по `source_listing_id`;
- получение/разрешение VIN, если требуется;
- запуск покупки отчёта;
- подтверждение стоимости перед покупкой;
- получение результата;
- сохранение исходного файла/данных;
- retry-механизм;
- защита от повторной покупки;
- обработка CAPTCHA/2FA/истечения сессии в рамках допустимого сценария интеграции;
- технический audit log.

### 13. Связка `карточка → исторический отчёт` — НЕ ПОДТВЕРЖДЕНА

Это главный исследовательский риск.

Нужно доказать на одном реальном автомобиле цепочку:

`source_listing_id → конкретная машина → VIN/идентификатор → доступность отчёта → цена отчёта → покупка → полученный файл/данные`.

Пока эта цепочка существует как продуктовая гипотеза.

### 14. Report Pipeline — ЧАСТИЧНО КАК МОДЕЛЬ, КОДА НЕТ

Архитектура определена:

`Raw report → Parser → Translator → Normalizer → Analyzer → Avtocheck report`.

Определены основные нормализованные сущности и логика provenance.

Нужно реализовать:
- хранилище raw report;
- parser конкретного формата;
- словарь/translation layer;
- нормализованную event schema;
- правила сопоставления пробега;
- кузовные события;
- сервис;
- страховые события;
- confidence/provenance;
- анализ конфликтов между источниками;
- генерацию итогового JSON отчёта.

### 15. Report Viewer — ЧАСТИЧНО

Есть визуальная концепция отчёта на лендинге и примеры блоков.

Нужно:
- отдельная страница реального отчёта;
- vehicle header;
- общий итог;
- риски;
- хронология;
- пробег;
- ремонты;
- страхование;
- сервис;
- provenance;
- ограничения данных;
- состояние формирования;
- постоянный URL/ID отчёта.

### 16. Выдача клиенту / личный кабинет — НЕ ВЫПОЛНЕНО

Нужно:
- пользователь/заказчик;
- история заказов;
- страница статуса;
- повторное открытие купленного отчёта;
- уведомление о готовности;
- управление возвратом/ошибкой.

### 17. Реальные фотографии — НЕ ВЫПОЛНЕНО

Галерея и UX готовы принимать фотографии.

Нужно решить:
- откуда разрешено получать изображения;
- можно ли хранить их у Авточек;
- нужна ли прокси/кэш-система;
- как обновлять удалённые/заменённые изображения;
- формат thumbnails/original;
- CDN/object storage.

### 18. Дедупликация одного автомобиля между источниками — НЕ ВЫПОЛНЕНО

Поздний, но важный слой:
- VIN;
- набор фото;
- характеристики;
- город/продавец;
- временные признаки;
- source listing IDs.

Один физический автомобиль должен в перспективе иметь один `vehicle_id` Авточек и несколько внутренних listing-связей.

## Текущая оценка по этапам ROADMAP

### Этап A — MVP frontend: примерно 80%

Основной интерфейс, VIN, визуальная модель отчёта, каталог и карточка уже существуют. Остались полировка темы, реальный report viewer и позже mobile.

### Этап B — каталог: примерно 35%

Frontend каталога и карточки готов. Исследование источников начато. Collector, база, API, живой inventory и реальные фото отсутствуют.

### Этап C — заказ отчёта: примерно 15%

CTA и frontend-состояния есть. Order Service, quote, payment и серверные статусы отсутствуют.

### Этап D — автоматизация получения отчёта: примерно 0–5%

Есть архитектура и исследовательская гипотеза. Рабочего Source Worker пока нет.

### Этап E — автоматический отчёт: примерно 10–15%

Модель и UX продуманы. Реального pipeline и report viewer пока нет.

### Этап F — масштабирование: 0%

К этому этапу переходить рано.

## Что считать настоящим ядром Авточек

Минимальное рабочее ядро должно уметь выполнить одну полную транзакцию без ручной подмены данных:

1. Получить реальную машину из inventory.
2. Создать внутренний `vehicle_id` и сохранить source linkage.
3. Показать эту машину на Авточек.
4. Получить запрос отчёта.
5. Вернуть реальную стоимость/доступность.
6. Получить подтверждённую оплату клиента.
7. Создать `paid` order.
8. Получить исходный отчёт по выбранной машине.
9. Сохранить raw report.
10. Автоматически преобразовать его в структуру Авточек.
11. Отдать клиенту постоянный готовый отчёт.

Пока хотя бы одна из точек 1–11 требует ручной подмены, это MVP-каркас ядра.

## Рекомендуемый следующий порядок

### P0 — доказать техническую цепочку источника

На одном реальном автомобиле доказать:
`listing → идентификатор/VIN → report availability → report price → purchase → raw report`.

Без этого нельзя уверенно проектировать Source Worker и экономику заказа.

### P1 — создать backend foundation

Минимум:
- API server;
- PostgreSQL;
- `vehicles`;
- `vehicle_listings`;
- `vehicle_photos`;
- `report_quotes`;
- `report_orders`;
- `raw_reports`;
- `reports`;
- job queue;
- object storage для файлов/фото.

### P2 — подключить первый Catalog Collector

Один источник, один формат, ограниченная выборка. Сразу нормализовать в `VehiclePublicDTO`.

### P3 — перевести текущий каталог и `vehicle.html` с demo-массива на API

После этого frontend впервые станет работать на живом inventory.

### P4 — реализовать Quote + Order

`vehicle_id → quote → payment → paid order`.

### P5 — реализовать Source Worker

`paid order → source purchase → raw report`.

### P6 — реализовать первый parser/report pipeline

Поддержать один реальный формат отчёта целиком.

### P7 — создать отдельный Report Viewer

Показывать клиенту реальный нормализованный результат.

### P8 — добавить delivery и личный кабинет

История заказов, статусы, повторный просмотр, ошибки и возвраты.
