# Авточек — Catalog Collector

Дата фиксации: 2026-08-19.

## Задача

Найти рабочий способ наполнять каталог Авточек реальными автомобилями из Китая так, чтобы:

- пользователь видел карточку только в интерфейсе Авточек;
- внешняя площадка, её логотип и ссылка не показывались в публичной карточке;
- источник и исходный listing сохранялись внутри backend;
- цена, пробег, фото, город и статус наличия обновлялись;
- для каждой машины существовал стабильный `vehicle_id` Авточек;
- позже к этой же машине можно было привязать заказ исторического отчёта.

## Решение после исследования

Для production не строить ядро на скрытом массовом scraping Che168/Autohome или Dongchedi.

Причины:
- у Che168/Autohome правила прямо ограничивают автоматическое получение и повторное использование контента без разрешения;
- у Dongchedi Enterprise Open Platform автоматический доступ допускается только в рамках предоставленных платформой сервисов и разрешений;
- даже если технически HTML можно разобрать, это плохая основа для коммерческого каталога: права на фотографии, rate limits, CAPTCHA, изменение DOM и блокировки делают канал нестабильным.

Основной путь для Авточек:

`разрешённый inventory feed / API / экспорт партнёра → Catalog Collector → нормализация → база Авточек → публичный API → cars.html / vehicle.html`

## Наиболее сильный кандидат №1: Jinyutang + Carzan

### Jinyutang / 金鱼塘

B2B-сеть китайских продавцов автомобилей с большим реальным inventory. Публичный официальный сайт заявляет сотни тысяч актуальных автомобилей, множество городов и ежедневное пополнение. Сервис ориентирован на профессиональных продавцов и B2B-торговлю.

### Carzan / 车小赞

Экспортная SaaS-платформа той же экосистемы. Ключевые свойства, которые совпадают с задачей Авточек:

- ERP управления автомобилями;
- собственный брендовый сайт;
- цифровая витрина;
- поиск автомобилей;
- работа с экспортными компаниями;
- связь с Jinyutang;
- заявлена синхронизация и совместное использование подходящих автомобилей в реальном времени;
- поддерживается сценарий собственного брендового frontend.

Это делает экосистему Jinyutang/Carzan самым логичным первым кандидатом для официального data-feed партнёрства.

## Что требуется запросить у Carzan / Jinyutang

Нам нужен read-only канал inventory для собственного frontend Авточек.

Минимальный запрос:

1. Есть ли API, webhook, CSV/Excel export, SFTP feed или иной разрешённый способ получать доступные автомобили.
2. Можно ли получать только активные автомобили и события снятия с продажи.
3. Какие поля доступны:
   - внутренний ID автомобиля;
   - марка;
   - модель;
   - комплектация;
   - год;
   - первая регистрация;
   - пробег;
   - цена;
   - город;
   - цвет;
   - двигатель;
   - коробка;
   - привод;
   - количество владельцев/переоформлений;
   - VIN полностью или частично;
   - фотографии;
   - inspection/condition data;
   - дата публикации;
   - дата обновления;
   - статус наличия.
4. Разрешено ли показывать предоставленные фото и данные на собственном сайте под брендом Авточек.
5. Требуется ли показывать название Jinyutang/Carzan публично.
6. Разрешено ли хранить фотографии в нашем object storage/CDN.
7. Можно ли использовать исходный ID автомобиля для последующих операций/заказов.
8. Есть ли sandbox/test account.
9. Цена интеграции и требования к китайскому юридическому лицу/дилерской регистрации.

## Резервный путь №2: прямые feed от китайских продавцов

Если агрегатор не даст подходящий API, Catalog Collector должен принимать данные напрямую от продавцов.

Поддерживаемые способы:

- JSON API;
- webhook;
- CSV;
- XLSX;
- SFTP;
- ручной import через админку как временный вариант.

Это позволяет подключать реальные стоянки по одной без зависимости от конкретной площадки.

Продавец даёт Авточек разрешение на публикацию данных и фотографий, а техническая запись внутри backend хранит источник.

## Резервный путь №3: 58 Open Platform

У 58 есть официальный Open Platform и отдельный автомобильный API-сценарий. Документация подтверждает API-интеграции в автомобильном разделе и возможность быстро публиковать/обновлять inventory.

Требуется отдельно подтвердить направление доступа: нужен export/read inventory из экосистемы 58 в Авточек, а не только загрузка нашего inventory в 58.

До такого подтверждения 58 остаётся исследовательским кандидатом.

## Che168 / Autohome и Dongchedi

Использовать для:

- исследования структуры карточек;
- тестовых референсов;
- сравнения полей;
- поиска потенциальных продавцов для прямого партнёрства.

Не использовать как production-канал массового скрытого scraping без отдельного разрешения или официального API/договора.

## Архитектура Catalog Collector

Collector не должен знать о frontend.

```text
Provider Adapter
    ↓
Raw Listing
    ↓
Validator
    ↓
Normalizer
    ↓
Vehicle Matcher
    ↓
Database
    ↓
Public Vehicle API
```

### Provider Adapter

Каждый источник реализует один контракт:

```text
listChanged(since)
getListing(source_listing_id)
getPhotos(source_listing_id)
getStatus(source_listing_id)
```

Типы adapter:

- `api`;
- `webhook`;
- `csv`;
- `xlsx`;
- `sftp`;
- `manual`.

## Public DTO

Frontend получает только объект Авточек:

```json
{
  "vehicle_id": "veh_...",
  "title": "Audi A6L 45 TFSI",
  "year": 2022,
  "mileage_km": 29000,
  "price": 252800,
  "currency": "CNY",
  "city": "Linyi",
  "status": "available",
  "photos": [],
  "specs": {},
  "report_available": null,
  "updated_at": "..."
}
```

Никаких `source_id`, `source_url`, названия площадки или логотипа во frontend DTO нет.

## Правила актуальности

Для первой версии:

- активный inventory обновлять каждые 1–6 часов, если источник это допускает;
- карточка без подтверждения `last_seen_at` более 24 часов получает `availability = stale`;
- после 48 часов без подтверждения предложение скрывается из публичного каталога;
- изменение цены создаёт snapshot;
- удаление listing переводит его в `sold_or_removed`, физический `vehicle` не удаляется.

## Фотографии

В production использовать фотографии только при наличии права отображать их.

Предпочтительная схема:

`licensed source photo → image worker → object storage/CDN → Авточек`

Хранить:

- оригинальный source URL;
- checksum;
- наше CDN URL;
- порядок;
- дату последней проверки.

## Что можно сделать до получения API

1. Реализовать таблицы и Provider Adapter interface.
2. Сделать `manual/csv` provider.
3. Перевести текущий frontend DEMO_VEHICLES на `GET /api/vehicles`.
4. Подготовить импорт одного разрешённого CSV от продавца.
5. Подготовить Jinyutang/Carzan adapter как пустой interface до получения credentials.

Так backend не придётся переделывать при подключении реального источника.

## P0 для запуска реального каталога

Успех Catalog Collector считается доказанным, когда выполняется цепочка:

```text
один разрешённый источник
→ минимум 100 реальных активных автомобилей
→ реальные фотографии
→ внутренний source_listing_id
→ нормализованный vehicle_id
→ автоматическое обновление цены/наличия
→ снятая машина исчезает с Авточек
→ пользователь открывает vehicle.html по vehicle_id
```

## Решение на сегодня

1. Основным коммерческим кандидатом считать Jinyutang/Carzan.
2. Запросить у них разрешённый inventory feed/API и право white-label показа фото и карточек.
3. Параллельно строить Catalog Collector через универсальный Provider Adapter.
4. Первым полностью рабочим adapter сделать CSV/XLSX, чтобы реальный продавец мог подключиться без API.
5. Che168/Dongchedi оставить исследовательскими и discovery-источниками до получения отдельного разрешения.

Таким образом мы можем строить код Collector уже сейчас, а конкретный коммерческий источник подключить без изменения ядра.
